# 架构与设计取舍

这份文档回答两个问题：**代码为什么这么分层**，以及**AI 在系统里负责什么、不负责什么**。
面试验收时，对方最可能追问的也正是这两件事——"你说你用了 AI，那 AI 到底做了什么决定"。

---

## 1. 一句话说清系统在做什么

> 输入一场面试的过程信号（简历、回答文字、画面帧、语音事件）→ 输出一份可追溯的分析报告（分数 + 证据 + 风险 + 成本）。

**明确不做**：不做录用判断，不给人打"过/不过"，不接 ATS 后续流程。所有输出都定位为"给面试官的观察记录与建议"。
这条边界写在每一份报告页脚（`app/report/builder.py` 的 `LIMITATIONS`），不是文档里说说而已。

---

## 2. 分层：一条数据从哪来、到哪去

```
┌─────────────────────────────────────────────────────────────────┐
│  展示层  app/templates/*.html + app/static/*.js                 │
│  三个页面：控制台（建场次）/ 面试页（问答 + 摄像头）/ 报告页     │
└───────────────────────────┬─────────────────────────────────────┘
                            │ HTTP / WebSocket（只推不改状态）
┌───────────────────────────▼─────────────────────────────────────┐
│  接口层  app/main.py                                            │
│  22 条路由：建场次、答题、送帧、参数调整、结束、报告、导出、配额  │
│  只做三件事：解请求 → 调领域服务 → 拼响应。不含业务判断           │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│  领域层（业务规则的唯一归属地）                                  │
│  ├─ api/session.py      会话生命周期、每轮跑图、兜底判定         │
│  ├─ agent/               LangGraph 状态机：出题→分析→决策        │
│  ├─ intake/              简历解析、上一轮报告吸收（结构化）       │
│  ├─ scoring/engine.py    8 维度评分规则（纯函数，无 IO）          │
│  ├─ vision / audio/      画面与语音的指标提取                     │
│  ├─ report/              报告拼装 + 三出口导出                    │
│  └─ billing/             配额、预算熔断、审计                     │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│  基础设施层  db.py（SQLite，6+3 张表）/ providers/llm.py（模型网关）│
│  唯一允许出现 SQL 与 HTTP 调用的地方                              │
└─────────────────────────────────────────────────────────────────┘
```

**分层的检验标准**：能不能单独替换掉某一层。
- 换数据库 → 只改 `db.py`（`SCHEMA` 集中管理，注释里写明换 Postgres 要动哪几处方言）。
- 换模型供应商 → 只改 `providers/llm.py`，其它层只认 `LLMResult`。
- 换评分口径 → 只改 `scoring/engine.py`，它不读库不联网，纯输入输出。
- 加一种导出格式 → 只加一个函数进 `report/export.py` 的 `EXPORTERS`。

## 3. AI 的边界：模型只做两件事

这是整套设计里最重要的一条。**分数不是模型打的。**

| 环节 | 谁做 | 为什么 |
| --- | --- | --- |
| 出题、追问、压力题、条件变更题 | **模型**（`PROMPT_QUESTION` 等 4 个结构化提示词） | 需要理解简历内容和上一轮缺口，规则写不出来 |
| 从一段回答里抽证据（关键论点/有无数字/有无举例/是否跑题/回避词） | **模型**（`PROMPT_ANALYZE_ANSWER`） | 这是自然语言理解，规则只能做关键词匹配 |
| 把证据聚合成 0–100 分 | **代码规则**（`scoring/engine.py` 的 8 个 `score_*` 函数） | 分数必须可复现、可解释、可审计。同一份证据今天 78 分、明天 74 分，面试官没法用 |
| 判断"够不够证据出分" | **代码规则**（`MIN_EVIDENCE = 3`） | 证据不足时返回 `status=insufficient_evidence` 而不是 0 分 |
| 画面里有没有人脸 / 看没看镜头 | **本地启发式**（`vision/analyzer.py`，Pillow + numpy） | 每帧调模型太贵；而且这里只需要"肤色连通域在哪"这种几何判断 |
| 画面语义（头部朝向、是否离席） | **模型**（默认关闭，`SI_VISION_USE_MODEL=0`） | 开了才有价值，但一场 400 帧约 ¥1.36，占成本 57%，默认关掉并要求显式打开 |
| 上轮报告 → 本轮追问点 | **代码规则**（`intake/report.py`） | "哪些维度证据不足"是集合运算，让模型转述只会引入失真 |

**一句话总结**：模型负责"读懂人说了什么"，代码负责"算出多少分"。
这样模型换代、换供应商、某次调用失败降级，都不影响历史报告的一致性。

### 3.1 模型失败的降级链

```
真实模型调用 → 失败/超时/JSON 解析不了 → 降级 MockProvider（规则实现）→ 打标 error
                                              ↓
                                     报告里 provider 字段标注来源
```

降级不是"静默成功"。每次降级都在 `llm_call` 表留一条记录（`ok=0` + `error`），
报告页的成本卡片会显示"其中 N 次走了规则化实现"。

### 3.2 预算熔断

`billing/guard.py` 的 `GuardedProvider` 包在真实 provider 外面：

- 每次调用前 `guard.allow(estimate)`，超预算就不调模型、直接给规则实现的结果。
- **刻意不中断面试**。候选人答到一半被系统踢出去，比多花两毛钱严重得多。
- 熔断次数进报告，客户能自己判断"这场数据有多少来自模型"。

## 4. 为什么每轮跑一次图，而不是整场一个长图

LangGraph 可以做成 `START → 出题 → interrupt(等回答) → 分析 → ...` 的长会话。这里没这么做。

| | 整场一个长图 + interrupt | **每轮跑一次图（当前）** |
| --- | --- | --- |
| 进程重启 | 依赖 checkpointer 恢复，恢复失败整场丢 | 状态在 DB，重建 state 即可继续 |
| 单测 | 要 mock interrupt，难写 | 纯函数 `run_turn(state, config, provider)`，直接断言 |
| 重放 | 难 | 同一份 turn 数据重跑得到同一份报告 |
| 代价 | — | 跨轮规划（"该插压力题了吗"）要在 state 里显式维护 |

选了后者，因为**面试是长事务，进程会重启，而面试官不能接受"刚才那场没了"**。

图的结构（`app/agent/graph.py`）：

```
START → prepare（算 plan：还剩几道主题、该不该插压力/变更题）
          ↓
       按 submitted 分流 ──False──→ generate（出新题）→ END
          │True
          ↓
       analyze（抽证据）→ decide（追问？压力？下一题？收尾？）
          ↓                          ↓
       conditional ──closing──→ closing → END
                   └─其余──────→ END（题面已由 decide/generate 写好）
```

`submitted` 这个字段是为一个真实 bug 加的：原来用 `answer == ""` 判断"首轮还是后续轮"，
结果候选人**提交空回答**（网络断了）和**首轮开始**在 state 里长得一模一样，
空回答直接走了"出新题"而不是"追问确认"。加了显式标志位才修好。

## 5. 数据模型：为什么是这些表

| 表 | 性质 | 说明 |
| --- | --- | --- |
| `interview` | 快照 | 一场面试的元信息 + 配置 JSON + 材料 JSON |
| `turn` | 事件（append-only） | 每轮问答。`UNIQUE(interview_id, idx)` 保证不重号 |
| `vision_frame` | 事件 | 每次抽帧的结果。只存指标不存图片（隐私 + 体积） |
| `audio_event` | 事件 | 转写片段、停顿、语速采样 |
| `llm_call` | 账本 | 每次模型调用的 token/耗时/成败，成本核算的唯一数据源 |
| `dimension_score` | 快照 | 报告生成时写入，避免每次看报告都重算 |
| `tenant` / `tenant_usage` / `audit_log` | 商业化 | 配额、用量、审计 |

**事件表 append-only**，是因为面试过程要能重放：
报告里的每一个分数都要能追到具体某几轮的哪几句话。如果允许改历史记录，审计就断了。

**为什么材料存 JSON 不拆表**：简历解析结果是嵌套结构（项目 → 要点 → 技术栈），
拆成关系表要 3 张表 + 6 次 JOIN，而它只在建场次时写一次、每轮读一次。
用 JSON 列是拿"不能按技能字段做索引"换"读写都只碰一行"，这个规模下划算。

## 6. 扩展点：加一个维度要改哪里

这是"可维护性"最实在的答案——不是口号，是具体步骤数。

**加一个第 9 个维度（比如"逻辑性"）**，共 4 步：

1. `app/config.py` 的 `DIMENSIONS` 加一项（key/name/weight/definition/evidence/scale）。
   注意模块底部有 `assert abs(sum(weight) - 1.0) < 1e-9`——加了权重要同步调平，否则**导入即失败**。
2. `app/scoring/engine.py` 写一个 `score_logic(ctx) -> DimScore`，按"证据不足返回
   `insufficient_evidence`"的既有约定实现，然后加进 `SCORERS` 映射。
3. `app/providers/llm.py` 的 `PROMPT_ANALYZE_ANSWER` 输出 schema 里补这个维度的证据字段。
4. 跑 `python -m unittest discover -s tests`——`test_fallbacks.py` 里有"没有对应环节就不该出分"
   的用例，新维度如果破坏了这条不变量会立刻红。

**换一个模型**：一个环境变量。`SI_TEXT_MODEL` / `SI_VISION_MODEL` / `SI_OMNI_MODEL`。
价目表在 `PRICING` 里按前缀匹配（`price_of()`），新模型没登记价格时会进 `unpriced_models`
并在报告里标出来——**"成本 ¥0" 和 "我不知道多少钱" 必须能分开**。

**换数据库**：`db.py` 的 `SCHEMA` 是单个字符串常量，方言集中在 `connect()` 和少数几处
`ON CONFLICT`。换 Postgres 要动的地方在注释里列了。

## 7. 四种异常兜底：不是"降级成能跑"，是"降级成能说清楚"

需求里点名了四种：面试时长 0、候选人中途离开、录音为空、网络中断。
实现在 `app/api/session.py` 的 `detect_fallbacks()`，判定口径是**只看候选人侧信号**：

| 异常 | 判定 | 报告怎么呈现 |
| --- | --- | --- |
| 时长 0（开了就结束） | `ended` 且 `duration < 1.0`，或一题都没答 | verdict=`insufficient_data`，明说"这场没有有效作答，不出分" |
| 候选人中途离开 | 连续无人脸 ≥ 20s（`AWAY_SECONDS`） | 记 `candidate_left` + 离开时长，风险信号升档 |
| 录音为空 | 有作答但 `total_chars == 0` | 记 `empty_audio`，语音类指标全部标"无数据" |
| 网络中断 | 候选人侧最后活动距今 > 180s（`STALL_SECONDS`） | 记 `disconnected`，报告标注"本场在 N 分钟处无后续信号" |

**两个坑值得记**：
- "最后活动时间"最初把 `asked_at`（服务端出题时间）也算进去了。服务器问完题在等人答，
  这段等待天然存在，导致 180 秒这个阈值几乎永远触发不了。改成只统计 `answered_at` +
  画面帧 + 音频事件才对。
- "时长 0"的判定最初写成 `duration < 1.0 or not answered`，结果**每场刚开始的面试**
  （duration 当然 < 1s）都被误判成异常。加上 `ended` 前提才正确。

**兜底的核心原则**：任何一条分支都不能让流程卡死。宁可出一份"数据不足"的报告，
也不能让面试官盯着转圈。

## 8. 商业化：三件事做实，三件事明确不做

**做实**：
1. **按场次配额**（`tenant_usage` + `monthly_quota`）——这是最容易卖的单位。
   超限返回 **402** 而不是 500，并带上 `used/limit/period/plan`，前端能直接引导升级。
2. **单场预算熔断**（`BudgetGuard`）——防止一次异常重试把账单打爆。
3. **审计日志**（`audit_log`）——建场次、结束、熔断都留痕。To B 客户第一个问的就是"能不能查谁用了"。

**不做**：支付/发票（接第三方）、强多租户隔离（现在共用一个 SQLite，上生产要拆库）、
SSO（企业客户会要求，但不是 demo 阶段的事）。

**成本模型**（`tools/e2e_api.py` 同款口径，20 分钟标准场）：

| 用途 | 调用次数 | 费用 |
| --- | --- | --- |
| 文本（出题/分析/决策） | 33 | ¥0.04 |
| 视觉（每 3 秒一帧，仅当开关打开） | 400 | ¥0.50 |
| 实时语音（Qwen-Omni 双向流） | 20 分钟 | ¥1.00 |
| **合计** | **434** | **≈ ¥1.54** |

结论：**钱几乎全花在视觉和语音上**，文本推理可以忽略。
所以降本的正确做法是降采样率（3 秒 → 8 秒一帧约 1/3 成本）和 VAD 门控，
而不是换更便宜的文本模型——那省下的钱不到 3%。

## 9. 多端：现在到哪一步

| 形态 | 状态 | 说明 |
| --- | --- | --- |
| Web 桌面 | ✅ 完整 | 主形态 |
| 手机浏览器 | ✅ 可用 | CSS 在 900px / 640px 两档断点；摄像头走 `getUserMedia`，手机浏览器需要 HTTPS 或 localhost |
| PWA（可加到主屏） | ✅ 已配 | `manifest.webmanifest` + `theme-color` + `apple-touch-icon` |
| 原生 App | ❌ 远期 | 需要原生摄像头/录音权限管理，Web 方案已能覆盖演示 |
| 小程序 | ❌ 远期 | 小程序不能直接用 `getUserMedia` 和 Web Speech API，要重写采集层 |

**为什么不现在做 App/小程序**：需求原文把这两项列在「二、阶段完成」的"远期不计入"里，
且真正的工作量在采集端重写，而不是业务逻辑复用。

## 10. 已知局限（主动交底）

1. **视觉是本地启发式**，不做人脸识别、不做情绪识别。"看镜头"是几何判断，受角度和光线影响，只作风险提示。
2. **肢体识别没做**，只做了"画面在不在动"（帧间差分）。这一点必须主动说，不要让人以为做了姿态估计。
3. **读稿风险是间接推断**（视线偏离 + 停顿比例 + 书面语密度），不是 OCR/提词器检测。
4. **耐心/抗压/适应力必须存在对应环节才出分**。没插追问题就没有耐心分，这是设计不是 bug。
5. **服务端 ASR 不可用**：当前账号下 `paraformer` 全系、`qwen3-asr-flash-realtime` 等都调不通，
   所以转写走浏览器 Web Speech API（Chrome/Edge 可用，Firefox 不支持）。
6. **SQLite 单机**：并发几百场没问题，但多实例部署要换 Postgres 并把 `_lock` 换掉。
