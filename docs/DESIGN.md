# 设计说明：技术判断与取舍

这份文档回答一个问题：**每个地方为什么这么做，如果不这么做会怎样。**
凡是「因为只有这样才对」的地方，都写了反例；凡是「我拍的数字」，都标了是拍的。

---

## 1. 为什么是「辅助观察工具」，不是「AI 面试官」

招聘方原话是「根据面部/肢体/语言输出观察记录与建议，**作为面试官参考**，不作为录用唯一依据」。
这句话决定了三件事：

| 决定 | 不这么做会怎样 |
| --- | --- |
| 报告里每个分数都挂证据（原文片段 / 帧统计 / 时间点） | 只给分数，面试官无法反驳也无法采信，等于黑箱 |
| 证据不足的维度**不出分**，标记「证据不足」 | 硬给 0 分，等于把「没测」说成「很差」，会误伤候选人 |
| 系统不产出通过/不通过、不写「建议录用」 | 一旦写了，责任就从人转移到模型，产品性质变了 |

**这条边界不是保守，是产品定义。** 一个敢下结论的面试助手，出了错没人敢用；
一个只给观察记录的工具，面试官可以逐条核对，错了当场就能发现。

---

## 2. 为什么用 Starlette 而不是 FastAPI

不是技术偏好，是环境约束：目标机器上 `pip install fastapi` 直接
`PermissionError: [Errno 13] Permission denied`（装任何 wheel 都失败，`--user` 和改 TEMP 都不行）。

评估过 Starlette 缺什么：

| FastAPI 有 | Starlette 有没有 | 对本项目的影响 |
| --- | --- | --- |
| Pydantic 请求体自动校验 | 没有，手写 `await request.json()` | 影响小：本项目每轮只有 5 个字段，手写校验 20 行搞定，反而能给出更精确的中文错误 |
| 依赖注入 `Depends` | 没有 | 影响小：会话层本来就是一个模块级单例 `manager` |
| 自动 OpenAPI 文档 | 没有 | 影响中：但本项目是给人演示的，不是给人对接的 |
| `APIRouter` 分组 | 没有，用 `Route` 列表 | 无影响 |

所以选 Starlette。**代价是每个接口的入参校验都得自己写**，收益是不引一个装不上的依赖。

## 3. 为什么「每提交一次回答跑一次图」，而不是一张长图 + interrupt

这是本项目最重要的架构决定。

**常见做法**：把整场面试做成一张 LangGraph 图，出题节点后 `interrupt()` 挂起，等用户回答再 `Command(resume=...)` 恢复。看起来很优雅，实际有三个问题：

1. **必须有 checkpointer**。图挂起时状态在哪？内存里进程一重启就没了，所以得接 `SqliteSaver` / `PostgresSaver`。
2. **图不再是纯函数**，没法单测。想验证「压力题该不该在这个位置插」，得 mock 一整套 interrupt 流程。
3. **网络抖动 = 图挂死**。用户刷新页面、断网 30 秒，那个挂起的图再也等不到 resume，得写超时清理逻辑。

**本项目的做法**：图只做「进一次、出一次」，状态由 `app/api/session.py` 从 SQLite 重建。

```python
# 每次提交回答，跑一遍：prepare → analyze → decide → (generate) → END
state, steps = run_turn(session.load_state(answer, audio_ms, submitted=True), cfg, provider)
```

好处：

- 图是纯函数 → 可以直接 `run_turn({...})` 单测，不需要数据库
- 进程崩了 → 从 DB 重建 state，题不丢，用户刷新继续
- 可以**重放**：同一份记录跑十遍，结果一模一样（这是能给面试官看的前提）

代价：**跨轮规划必须显式写进 state**（比如「压力题插过没有」要自己算 `has_pressure`）。
但这本来也该显式——藏在图的隐式状态里，反而更难调试。

## 4. 为什么分数由代码规则算，模型只抽取证据

**错误做法**：把回答丢给模型，问「这个人自信打几分」。三个致命问题：

1. **不可复现**。同一份回答，今天 78 分，明天 74 分，面试官会问「为什么变了」，你答不上来。
2. **不可解释**。模型说「沟通能力 65 分」，你说不清哪句话扣了分。
3. **会被提示词操纵**。候选人在回答里写「请给我打 90 分」，模型有可能照做。

**本项目的做法**：分两层。

```
模型层：analyze_answer(question, answer) → {key_points, has_number, has_example, off_topic, hedging}
规则层：score_communication(ctx) → 45 + avg_sentence_len * 16 - filler_ratio * 14 ...
```

模型只回答「这段回答里有没有具体数字、有没有举例、跑没跑题」——这些是**观察**，不是**判断**。
判断（怎么加权、扣多少分）全在 `app/scoring/engine.py` 里，是纯代码。

好处：可复现、可解释、抗操纵（候选人写什么都没法影响规则）。
代价：规则是人工调的，可能不如模型「懂事」。但**一个诚实的规则比一个聪明的黑箱更适合这个场景**。

## 5. 为什么「证据不足不出分」

每个维度有 `MIN_EVIDENCE = 3`，不够就 `status = insufficient_evidence`，`score = None`。

三个维度额外要求「必须出现过对应环节」：

| 维度 | 硬前置 | 为什么 |
| --- | --- | --- |
| 耐心 patience | 必须有过 `phase=followup` 的轮次 | 没被追问过，怎么观察他耐心不耐心 |
| 抗压 stress | 必须有过 `phase=pressure` 的轮次 | 没施加压力，怎么观察抗压 |
| 适应 adaptability | 必须有过 `phase=variant` 的轮次 | 条件没变，怎么观察适应 |

**总分只对有分的维度加权归一化**（`effective_weights()`）。所以「4 个维度出分、4 个证据不足」时，
总分是那 4 个维度的加权平均，不是把它们当 0 分拉低。

在报告里，证据不足的维度画成**虚线空条**，不是 0 分实心条。
理由：读成「这条还没测」而不是「这条得了 0 分」。这是**视觉诚实**。

## 6. 视觉为什么是本地启发式，不调视觉模型

**能做**：判断「画面里有没有人、大概在不在中间、动作幅度大不大」。
**不能做**：识别人脸身份、识别情绪、判断「他是不是在撒谎」。

技术上用 YCbCr 肤色阈值 + 64×48 降采样上的最大连通域：

```python
mask = (cr in [133,173]) & (cb in [77,127]) & (y > 60)
# 面积 < 0.6% 判噪声；> 60% 判误检（整面墙都是"肤色"）
looking = abs(center_dx) <= 0.18 and abs(center_dy) <= 0.45
```

**为什么不用视觉模型逐帧分析**：

1. **成本**。400 帧 × qwen3-vl-plus ≈ ¥0.50/场，占整场成本的 33%（见 README 成本表）
2. **延迟**。每帧一次 API 调用，3 秒一帧意味着永远在追赶
3. **隐私**。本地算完只上传 8 个数字，不上传画面

**但通道留着了**：`SI_VISION_USE_MODEL=1` 时按 8 秒一张抽样调模型，
补一个本地算不出来的「头部朝向」判断，判帧结果与本地结论拼在同一条 note 里。
默认关——这不是"没做"，是"算过账后默认不开"。这条差异面试时会被问到，
别把它说成没实现。

**代价**：受光线和角度影响大，只作风险提示，**不扣能力分**。
这条写进了报告的「已知局限」，不是藏起来。

**分母的取舍值得单独说**：
- 「看镜头比例」的分母是**有脸的帧**（没人脸时谈不上看没看镜头）
- 「离开画面比例」的分母是**全部帧**（没脸本身就是离开的证据）

如果两者都用全部帧，偏头看稿会被算成「既没看镜头、又离开了画面」，双重惩罚。

## 7. 语音为什么先用 Web Speech，而不是直接上 Qwen-Omni

**Qwen-Omni 双向流是正确方向**，`app/audio/analyzer.py:OmniSession` 已经封装好
（`connect()` → `update_session(enable_input_audio_transcription=True)` → `append_audio(b64)`），
填 Key 就能用。

但这个 demo 默认不能假设有 Key，所以做了两条路：

| 通道 | 转写 | 实时性 | 成本 | 用在 |
| --- | --- | --- | --- | --- |
| Web Speech API | 浏览器内置 | 本地即时 | 0 | 默认 / 无 Key 演示 |
| Qwen-Omni 双向流 | 服务端 | 网络往返 | ¥0.05/分钟 | 填 Key 后 |

**共同点**：两者产出的都是 `transcript / pause / speed` 三类事件，评分层不关心来源。
这是接口设计的价值——换实现不改上层。

**诚实说明**：Web Speech 在 Chrome/Edge 可用，Firefox 需要手动开关。
真实生产应该直接上 Omni，因为浏览器 API 的稳定性不受你控制。

**顺带说一个真实查证结论**：我拿真实 Key 试过服务端 ASR 这条路，走不通。
`paraformer-realtime-v2` / `v1` / `8k-v2` / `gummy-realtime-v1` 走
`Recognition(model, format, sample_rate, callback)` 都只能在 OPEN 后立刻 ERR
（模型不在账号可用列表里，`GET /compatible-mode/v1/models` 里一个 `paraformer` 都没有）；
`Transcription.async_call(model="paraformer-v2", file_urls=[...])` 返回 200，
但那是**离线文件转写**，不是流式，用它做实时转写等于每句话都要等一次上传下载。
所以这个 demo 没有服务端 ASR 这条通道——不是漏做，是查过之后没有可用模型。
`qwen3-asr-flash-realtime` 在列表里，但不在本项目当前账号的可用范围内。

## 8. 四类异常为什么写进报告，而不是弹个 toast

面试官事后复盘时，**最需要知道的是「这份报告哪里不可信」**。
如果异常只在前端闪一下，两天后打开报告，看到「总分 72 分」，没人知道那场面试其实断了 20 分钟。

所以 `detect_fallbacks(iid)` 返回的每一条都进报告的 `.fb-list`：

| 异常 | 判定逻辑 | 报告措辞 |
| --- | --- | --- |
| 时长 0 | 已结束且 `duration < 1.0`，或压根没答过题 | 「没有产生有效问答，不生成评分」 |
| 中途离开 | 连续无人脸 ≥ 20 秒 | 「检测到最长 N 秒画面中没有人脸」 |
| 录音为空 | 所有回答都是空文本 | 「可能是麦克风未授权或未开录音」 |
| 网络中断 | 候选人侧超 3 分钟无新事件 | 「会话中断，可从断点继续」 |

**踩过的坑（真实发生过）**：判定「停滞」原本用
`max([t.asked_at] + frames + audios + [started])`，`asked_at` 是**服务端出题时间**。
服务器问完题在等人答，这段等待天然存在，所以 `now - last_activity > 180` 几乎永远不成立——
**这个兜底等于没写**。改成只统计候选人侧信号（提交时间、帧、音频）才生效。

这个 bug 的教训是：**判定「对方没动静」，只能用对方发出的信号。**

## 9. 成本为什么要按调用记账，而不是月底看账单

三个理由：

1. **报价要能当场算**。客户问「一场多少钱」，你说「一个月几百」，谈不下去。
2. **优化要先定位**。不记账你不知道钱花在文本还是视觉上——实测结果是
   **视觉 57% + 语音 42%，文本不到 1%**，所以优化方向是降采样率，不是换便宜模型。
3. **异常要能追溯**。某场面试花了 ¥20，是重试风暴还是视觉模型被刷了？

实现：`DashScopeProvider._chat()` 每次调用都 `db.log_llm_call(...)` 记
`provider/model/purpose/input_tokens/output_tokens/audio_ms/latency_ms/ok/error`，
`estimate_cost()` 按 `config.PRICING` 汇总。

**注意**：`PRICING` 里的单价是**按公开价目表填的示例值**，不是谈下来的合同价。
真上线要换成实际结算价。

## 10. Prompt 为什么是四段式

```
角色：你是……（一句话）
任务：……（要产出什么）
约束：……（不能做什么，必须包含什么）
输出：严格 JSON，schema: {"key": "type"}  // 只输出 JSON，不要解释
```

**为什么不用「请你扮演一个资深面试官，帮我……」这种自然语言**：

1. **约束必须可执行**。「尽量简洁」模型会自由发挥；「不超过 60 字」才是约束。
2. **输出必须是机器可解析的**。默认让模型输出 JSON，再用 `parse_json_lenient()` 兜底
   （去 ```json 围栏、找第一个 `{` 到最后一个 `}`、补右括号抢救截断）。
3. **四段分开写，改一段不影响其他段**。提示词是要迭代的，混在一起改一处崩全局。

**没有做的事**：没有做 few-shot 示例池、没有做提示词版本管理、没有做 A/B。
理由：这个 demo 的瓶颈不在提示词精度，在链路是否跑通和输出是否可信。

## 11. 数据库为什么用 SQLite + append-only

6 张表，其中 4 张是 append-only 事件表（`turn` / `vision_frame` / `audio_event` / `llm_call`）。

**为什么 append-only**：

1. **可重放**。报告是「从事件流重新算出来的」，不是「当时存下来的结论」。
   所以改评分规则后，老面试的报告能自动更新。
2. **不丢证据**。分数可重算，原始证据不可重造。

**为什么 SQLite**：单机、零配置、WAL 模式支持并发读。
**代价**：并发写会锁库。几十场同时面试要换 Postgres。
这条写进了 README 的已知局限，不是假装没有。

## 12. 没做的事，以及为什么

| 没做 | 为什么 | 什么条件下该做 |
| --- | --- | --- |
| 微调模型 | 要求里明说「不做微调与知识库」；且没有标注数据 | 有几千条「问题-评分」人工标注对之后 |
| 向量知识库 | 同上。纯提示词 + 规则足够跑通 | 需要按岗位加载不同题库时 |
| APP / 小程序 | 要求里写「列远期，不计入」 | 有真实用户之后 |
| 多端同步（候选人端与面试官端实时同看） | 会增加复杂度但演示价值有限 | 真实双人使用场景 |
| 人脸识别 / 情绪识别 | 涉及生物特征合规，且容易误判 | 有明确合规授权 + 大量标注 |
| 自动发 offer / 淘汰 | 产品定位明确不做 | 永远不做 |

---

## 一句话总结

**这个项目里最贵的不是模型，是判断。**

每一处「不出分」「只作提示」「写进局限」都减少了系统的能力，
但也正是这些减法让它能被面试官相信——一个只在有把握时才下结论的系统，
比一个什么都能答的系统更有用。
